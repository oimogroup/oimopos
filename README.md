# Oimo

SaaS-система для заведений общественного питания: каждая компания работает в изолированном аккаунте со своими заведениями, кассами, сотрудниками, поставщиками, складами, меню, финансами и продажами. Внутри аккаунта поддерживаются приходные поставки, расчёты с поставщиками, складские перемещения, инвентаризация, производство и порционная продажа через POS.

## Запуск

Для рабочего режима нужен Docker Desktop. HTML-файлы нельзя просто открывать с диска: вход и документы обслуживает API, а общие данные хранятся в PostgreSQL.

```bash
cp .env.example .env
python3 scripts/init_pin_key.py
docker compose up -d --build
docker compose ps
```

После запуска откройте <http://127.0.0.1:8000/> — публичный лендинг Oimo. Вход в систему: <http://127.0.0.1:8000/login>.

Лендинг содержит обзор продукта, актуальные тарифы и самостоятельную регистрацию. Имя, телефон, email, пароль и формат создают изолированный пустой аккаунт с одним заведением и пробной подпиской на 14 дней, затем пользователь автоматически входит в `/admin`. Срок и лимит задаются сервером; после истечения доступ блокируется до активации подписки владельцем платформы. Повтор регистрации с тем же идентификатором не создаёт дубль и не продлевает срок. Один телефон может создать один пробный аккаунт; дополнительно действует лимит 10 регистраций с сетевого адреса за час. Email и телефон не подтверждаются кодом, автоматической оплаты и восстановления пароля по email пока нет. Владелец может изменить доступ через `/platform`. Пароль не сохраняется в браузерном хранилище. Старый API заявок и блок «Заявки с сайта» сохранены для уже полученных обращений; новые регистрации сразу появляются в списке компаний.

Перед выкладкой примените миграцию `018_trial_registration` через `python /app/render_migrate.py` (на Render — Pre-Deploy Command). Удаление компании удаляет запись её пробной регистрации. Регистрация не создаёт демонстрационные продажи или остатки; настройка меню и кассы доступна в админке.

Почта: Gmail `oimogroup2027@gmail.com`, SMTP `smtp.gmail.com:465` с TLS. В Environment сервиса добавьте `SMTP_PASSWORD` — пароль приложения Google (нужна двухэтапная аутентификация); обычный пароль Gmail не подходит. Секреты не добавляются в репозиторий. На Render для SMTP нужен платный Web Service. При использовании порта `587` соединение обязательно переходит на STARTTLS. `PUBLIC_APP_URL` задаёт публичный HTTPS-адрес для ссылки входа; на Render по умолчанию используется `RENDER_EXTERNAL_URL`. Подробности настройки: https://support.google.com/mail/answer/185833?hl=ru.

Миграция `019_email_outbox` добавляет очередь писем. После регистрации создаётся приветственное письмо с логином и сроком пробного периода; пароля в письме нет. Очередь сохраняется в PostgreSQL в одной транзакции с аккаунтом, повтор регистрации не создаёт новое письмо. Веб-сервис сам отправляет её в фоне; отдельный worker на Render не нужен. Без `SMTP_PASSWORD` письма ждут в очереди и регистрация работает. После настройки предусмотрено до 6 попыток с интервалами; неудачные письма можно повторить в `/platform` → «Системная почта Oimo». Там же доступны статус очереди и тестовое письмо на SMTP_TEST_RECIPIENT. Статус «Принято почтовым сервером» означает приём SMTP, а не гарантированную доставку во входящие. После сбоя между приёмом SMTP и сохранением результата возможна повторная доставка с тем же Message-ID. Подтверждение владения email и восстановление пароля пока не реализованы.

После чистого запуска существует только системная учётная запись владельца SaaS-платформы: `platform` / `ChangeMe-Platform-2026`. Клиентский аккаунт, первое заведение, владелец аккаунта и основная касса создаются через мастер в кабинете платформы.

Перед реальной эксплуатацией обязательно замените все стартовые пароли в `.env` **до первого запуска базы**. Пароли хешируются на сервере, а браузер получает только защищённую `HttpOnly`-сессию. При изменении пароля кассы её старые сеансы отзываются.

Веб-интерфейс работает на порту `8000`, API — на `8001`, PostgreSQL — на `5432`. Порты и пароли меняются в `.env`.

## Рабочий процесс

Админ-панель сгруппирована по модели ресторанных POS-систем: «Меню», «Склад», «Финансы», «Статистика» и «Доступ». В «Доступе» отдельно настраиваются заведения, кассы и сотрудники. Внутри «Склада» находятся остатки, поставки, перемещения, списания, инвентаризации, производство, отчёт по движению и поставщики.

1. Владелец платформы входит в отдельный кабинет `platform.html` и проходит мастер подключения: создаёт аккаунт компании, заполняет профиль бизнеса, отдельно указывает название и адрес первого заведения, задаёт тариф и доступ владельца. Вместе с первым заведением автоматически создаётся основная касса.
2. Администратор клиента входит с выданными данными и видит только свою компанию.
3. Администратор компании завершает настройку первого заведения или создаёт дополнительные заведения. Для каждого заведения настраиваются склад, кассы, график и финансовый счёт; поставщики ведутся в общем справочнике аккаунта.
4. Сотрудники создаются в общем разделе аккаунта и получают должность. Руководитель, кладовщик, производство и маркетолог входят по личному логину и паролю; кассир, официант и администратор зала работают на кассе по личному PIN. Основное заведение сотрудника используется для смен и отчётов, но не создаёт отдельный аккаунт.
5. Перед продажей сотрудник выбирает своё имя на терминале и вводит PIN. Сеанс кассира действует до окончания сеанса терминала (по умолчанию 7 дней), смены кассира или закрытия смены. При закрытии смены действующий сеанс не требует повторного PIN. Если сеанс уже истёк, кассир выбран автоматически, а введённая сумма наличных сохраняется до подтверждения PIN. При смене кассира терминал остаётся авторизованным, а открытый чек очищается после подтверждения.
6. Ответственный сотрудник открывает «Склад → Поставки», выбирает склад и поставщика, переносит в одну приходную накладную все фактически полученные продукты, количество и закупочную цену.
7. При проведении поставки остаток выбранного склада увеличивается, а себестоимость каждой позиции пересчитывается по средневзвешенному методу.
8. Оплату можно не указывать, внести частично или разбить на несколько счетов. Оплаченная сумма автоматически появляется в движении денег, неоплаченный остаток — в долге поставщику.
9. Производство выпускает блюдо по техкарте в килограммах; сервер списывает сырьё выбранного склада.
10. Готовая партия передаётся на раздачу. Только после этого блюдо доступно кассиру порциями.
11. POS создаёт чек по серверной цене, записывает в него выбранного сотрудника и связывает проданные порции с партией на раздаче. Готовые закупные товары списываются со склада заведения.
12. При закрытии раздачи количество проданных порций берётся из кассы и не редактируется вручную.

Перемещение между складами проходит через запрос получателя, согласование, отгрузку склада-отправителя и фактическую приёмку склада-получателя. На время инвентаризации движения выбранного склада блокируются.

## Данные и безопасность

Раздел «Настройки» содержит общие параметры компании, информацию о подписке, заказы, доставку, ограничения действий сотрудников и шаблон чека. Настройки сохраняются в серверном состоянии компании и применяются после обновления кассы. Обслуживание, доставка и округление рассчитываются сервером; дробные порции учитываются в продажах, возвратах и закрытии раздачи. Изменение валюты не конвертирует существующие суммы. Логотип для чека — JPEG, PNG или GIF до 5 МБ.

Онлайн-оплата подписки, фискальный регистратор, налоги и табель рабочего времени пока не подключены; интерфейс явно показывает эти ограничения. Производство и кассовые смены обязательны для текущей модели учёта. Подтверждение защищённых действий выполняется входом по личному PIN управляющего или администратора зала.

- У каждой компании есть собственный `tenant_id`; рабочее состояние, пользователи, аудит и техкарты фильтруются сервером по этому идентификатору.
- Владелец платформы управляет компаниями и подписками, но не открывает их рабочие документы через обычный API.
- Администратор компании не может видеть список клиентов платформы или данные другой компании.
- Приостановка компании завершает все её активные сеансы.
- Тариф хранит лимит заведений и применяется сервером при создании нового заведения.
- Все рабочие документы и продажи хранятся в общей серверной базе, а не в `localStorage` браузера.
- Роль и права сотрудника проверяются API для каждого действия.
- Кассир не получает закупочные документы и себестоимость, производство не может проводить продажи, а кладовщик не может выпускать блюда.
- Пароли хранятся как `PBKDF2-SHA256`-хеши с индивидуальной солью.
- PIN кассира также хранится только как солёный хеш. После пяти неверных попыток ввод блокируется на пять минут.
- Сервер ведёт неизменяемый журнал складских движений и аудит действий пользователей.
- Номер накладной необязателен; если он указан, повторная накладная того же поставщика отклоняется.
- Администратор компании управляет заведениями, кассами и сотрудниками из отдельных реестров без переключения всего интерфейса в «режим точки».
- Несколько руководителей могут работать в одном аккаунте; искусственного правила «один управляющий на одно заведение» нет.

Для HTTPS-развёртывания установите `SESSION_COOKIE_SECURE=true` и публикуйте приложение через TLS-прокси. Текущий проект содержит SaaS-основу и локальный кабинет платформы; для публичного коммерческого запуска дополнительно нужны домен, HTTPS, управляемая PostgreSQL, автоматические резервные копии, почтовая доставка приглашений, мониторинг и интеграция с выбранным платёжным провайдером.

## Зарплата и рабочее время

Владелец открывает «Финансы → Зарплата». Для каждого сотрудника задаются дата начала, ставка за час, рабочую смену или календарный месяц и проценты. Личные продажи относятся к сотруднику, открывшему заказ; процент от продаж во время работы требует отдельной отметки рабочего времени. Можно задать проценты по категориям и от суммы обслуживания. База продаж учитывает скидки, исключает доставку и обслуживание; обслуживание рассчитывается отдельно.

На кассе сотрудник входит по личному PIN и выбирает «Функции → Рабочее время → Начать / закончить рабочий день». Кассовая смена и рабочее время независимы. Владелец может внести или исправить время с обязательным основанием. Исправление времени не пересчитывает уже зафиксированные проценты с чеков: для этого предусмотрена отдельная корректировка.

Порядок расчёта: выбрать завершённый период, проверить время и начисления, утвердить ведомость, провести полную или частичную выплату со счёта банка или сейфа. Авансы автоматически зачитываются при начислении. Выплаты отражаются в финансах; отмена создаёт обратный денежный документ и восстанавливает долг. Повторная отправка одного запроса не создаёт повторную выплату. Утверждённые периоды защищены от изменений и пересечений; поздний возврат чека уменьшает начисления текущего периода. Доступен экспорт CSV.

Ставки действуют с текущей или будущей даты; старые продажи автоматически не пересчитываются. Начальные остатки вносятся корректировкой. При прекращении работы сотрудника используйте удаление сотрудника после закрытия его рабочего времени: выключение доступа само по себе не прекращает месячную ставку. Это оперативный учёт начислений и выплат: налоги, удержания по законодательству и регламентированная отчётность не рассчитываются. Реализация не означает полного совпадения всех функций с Poster POS.

Проверки: `backend/tests/test_payroll.py`, `tests/payroll-smoke.html`, `tests/work-time-smoke.html`.

## P&L — прибыли и убытки

Владелец открывает «Финансы → Прибыль и убытки». Серверный отчёт показывает выручку за вычетом возвратов, сохранённую себестоимость проданного, валовую прибыль, прочие доходы, расходы по статьям, чистую прибыль и рентабельность. Фильтры выбирают календарные даты в часовом поясе компании и заведение; CSV в этой вкладке выгружает именно P&L. Остатки денег показаны отдельно.

Через «Добавить расход» вносится полная сумма и период, например аренда за 1–31 октября. Сумма распределяется по календарным дням с сохранением копеек. Неоплаченный расход уже уменьшает прибыль своего периода. После сохранения его можно оплатить полностью или частями со счёта банка или сейфа. Эти оплаты меняют деньги, не дублируя расход в P&L. Возврат оплаты создаёт обратный денежный документ, отмена неоплаченного расхода сохраняет историю.

Зарплата включается по ставкам и зафиксированным процентам за выбранный период независимо от даты выплаты и утверждения ведомости; выплаты и авансы из модуля зарплат второй раз не вычитаются. Открытые рабочие смены отмечаются предупреждением. Ручная зарплата и автоматическое начисление одновременно требуют проверки; если вручную проводится только оплата уже начисленного, отключите её влияние на прибыль.

Обычные финансовые операции по умолчанию относятся к дате оплаты; в дополнительных полях можно указать дату признания или выключить участие в прибыли (например, для кредита, вклада или изъятия владельца). Оплату расхода из P&L проводите через его запись, без второй отдельной операции. Закупки запасов, возвраты поставщиков и переводы между счетами не влияют на прибыль непосредственно. Списания подтверждённых партий и недостачи по журналам учитываются отдельно; расхождения витрины на проверке явно помечены. Общие расходы компании показываются во всей сети и не распределяются между заведениями автоматически.

Налоги учитываются по внесённым суммам, без автоматического расчёта по налоговому режиму. Исторические чеки без сохранённой себестоимости вызывают предупреждение: текущая цена каталога не выдаётся за историческую. Старые денежные операции сохраняют прежнюю дату признания до явной корректировки. Отчёт ограничен периодом до 367 календарных дней и не является регламентированной бухгалтерской отчётностью.

Проверки: `backend/tests/test_pnl.py`, `tests/pnl-smoke.html`.

## Автономная касса

После подготовки онлайн касса поддерживает новые продажи за наличные при недоступном облаке. Нужны HTTPS (или localhost), обычный профиль браузера, вход по личному PIN и открытая кассовая смена. В строке связи над каталогом должен появиться статус «Автономная касса готова». Доступ выдаётся сервером для конкретных компании, кассы, сотрудника и смены на 24 часа. PIN хранится только как локальный PBKDF2-верификатор; изменение версии учётной записи проверяется при синхронизации.

Приложение и локальная библиотека QZ кэшируются Service Worker только для терминала `/pos`; API и кабинеты в Cache Storage не попадают. Чеки и очередь хранятся в IndexedDB, подтверждение пользователю выдаётся после завершения записи. Один запрос оплаты сохраняет один идентификатор от устройства до сервера. После восстановления связи очередь отправляется автоматически и по кнопке, включая сверку ранее спорных чеков. После перезагрузки офлайн доступен вход по PIN, ранее проверенному онлайн на этом устройстве. Открытие/закрытие кассовой смены, возвраты, доставка, персональные скидки, складские операции и выплаты требуют сервера. Карта и QR офлайн не принимаются этим модулем. Максимум — 2000 неотправленных чеков на кассу.

Печать выполняется настроенным локальным способом; синхронизация и повторный вход не запускают повторную печать. У бумажного чека уникальный автономный код, который сохраняется в серверном чеке и доступен поиску в архивах. Физическая работа конкретного принтера подтверждается только пробным чеком на оборудовании.

Сервер сверяет чек по сохранённым ценам, фактическим остаткам, кассе, сотруднику и смене. Расхождения не удаляются: владелец видит их в «Финансы → Операции → Автономные чеки». Он проверяет остатки и при необходимости явно выбирает текущую открытую смену той же кассы с основанием. Если исходный серверный чек уже существует с другой суммой, владелец может принять его после сверки денег без повторного списания. После инвентаризации требуется отдельная проверка, чтобы не списать уже учтённое фактом количество повторно. Поздние зарплатные проценты из закрытых ведомостей относятся к открытому периоду синхронизации. До отправки всех чеков финансовый результат облака предварительный.

Не очищайте данные браузера и не удаляйте приложение с неотправленной очередью. В строке связи доступна выгрузка копии очереди без PIN, верификаторов и токенов доступа. Это файл для сверки и восстановления администратором; автоматического импорта этого файла нет. Неопределённые оплаты старой версии без привязки к кассе сохраняются отдельно для ручной сверки, а не автоматически отправляются из другого рабочего места. Перед обновлением приложения отправьте очередь и закройте старые вкладки терминала, чтобы новая версия Service Worker активировалась. При изменении файлов оболочки обновляйте версию `CACHE` в `pos-worker.js`; схему IndexedDB меняйте с миграцией, а не удалением очередей.

Проверки: `backend/tests/test_offline_pos.py`, `tests/offline-pos-core-smoke.html`, `tests/offline-review-smoke.html`. Локальные сквозные артефакты отключения сети и перезапуска: `.runtime/audit/offline-20261022`.

## Ограничения

Печать в POS поддерживает системный диалог, QZ Tray через драйвер и ESC/POS, бумагу 58/80 мм. Чек остаётся нефискальным. Для QZ Tray программа устанавливается на кассе отдельно; печать без запросов разрешения требует настройки сертификата. Подключение конкретной модели подтверждается пробным чеком; порядок настройки описан в `docs/terminal-production.md`. До эксплуатации потребуются интеграция с зарегистрированной ККМ, банковским терминалом, резервное копирование и HTTPS.

Остановка без удаления данных:

```bash
docker compose down
```

Команда `docker compose down -v` удаляет базу без возможности восстановления; используйте её только для осознанного сброса тестовых данных.

PIN-коды терминала проверяются по хешу. Для просмотра администратором новые PIN также сохраняются зашифрованными; просмотр выполняется отдельным запросом с проверкой прав и записью события без самого PIN. Старые хеши нельзя восстановить: сотруднику нужно явно назначить новый PIN. Ключ `.runtime/employee-pin.env` хранится отдельно от базы; сохраняйте его при переносе сервера и резервном копировании. Скрипт инициализации не заменяет существующий ключ.

## Логин кассы

В «Доступ → Кассы → Настроить» владелец компании может изменить **логин конкретной кассы**. Поле показывает настоящий логин терминала, а код компании отображается отдельно. Новый логин действует сразу, прежний перестаёт подходить для нового входа; пароль, PIN, действующий сеанс, смены и история не меняются. Изменение записывается в журнал. Код компании остаётся дополнительным способом входа с паролем выбранной кассы. Руководитель заведения может менять остальные доступные ему настройки, а логин назначает владелец. Основная касса создаётся при регистрации как начальное рабочее место; её имя, логин и пароль можно настроить.
